# M1.8-B1 validation: kinematic interface refactor

Status: **accepted and committed.** B1 is the frozen structural baseline for M1.8-B2.

Scope is the B1 stage only, as authorized in
[game/M1_8_B_PLAN.md](../../game/M1_8_B_PLAN.md) section 11. No context-dependent
distribution, no `room_kinematic_scale` value, no activity budget, no B2 work and no RL
is implemented. M1.7.1 and M1.8-A are untouched.

**Headline result: the refactor is bit-identical.** Across 7 deterministic scenarios and
4060 ticks, every recorded float matches the pre-B1 capture exactly, and every random
stream ends in an identical state. There is no first divergence, and no tolerance was
introduced or needed.

## 1. Architecture before and after

Before, `World._move_fly` interleaved three concerns in one function body: it arbitrated
between the neural action and the ecological command, applied the damping law inline, and
then integrated and constrained the result. The ecological command was read directly at
three separate points (`target_speed`, `eco_turn`, `spontaneous_clock_rate`), each
repeating the same `command is None or threat_priority` condition.

After, the concerns are separated into the chain the plan calls for:

```text
behavioral / ecological / lifecycle context
  -> KinematicResolver   : context -> KinematicProfile request
  -> KinematicProfile    : what the fly asks its body to do
  -> KinematicExecutor   : request -> body velocity and yaw
  -> World               : integration, collision, containment
```

`KinematicResolver` is pure: it holds only immutable body constants, performs no random
draw and mutates no state, so introducing it cannot perturb any RNG call order. The
arbitration condition now exists once, inside `KinematicResolver.airborne`.

Three relaxation laws are named rather than unified, because the accepted code uses two
distinct formulas whose floating-point operand grouping differs, and unifying them would
have forced a tolerance:

| Law | Used by | Update |
| --- | --- | --- |
| `DAMPED_CRUISE` | ordinary airborne flight | `a = k*(target*dir - v)`; `v += a*dt` |
| `EXPONENTIAL_APPROACH` | M1.8-A landing approach | `alpha = 1-exp(-dt/tau)`; `v += alpha*(target*dir - v)` |
| `DIRECT` | stationary contact, launches | WORLD sets velocity; executor does nothing |

`World.kinematic_profile` now carries a context identity for every tick
(`baseline_cruise`, `neural_priority`, `ecology_<state>`, `lifecycle_visual_approach`,
`lifecycle_stationary_contact`, `lifecycle_takeoff_voluntary`,
`lifecycle_takeoff_escape`). It is diagnostic only and is **not** written to any
recording in B1.

### 3.1 Negative control

A "bit-identical" result is only meaningful if the harness can detect a change. The
executor was temporarily perturbed by adding `1e-12` to `vx` — far below any behavioral
threshold — and the trace was re-captured:

```text
clean sha256  593755c92dd32b3d
dirty sha256  34adeacad1ae73ff
first_divergence: tick 0, column vx,
  before -0x1.48efec792fd5cp+3  after -0x1.48efec792faf5p+3
```

The perturbation was caught on the first tick. This confirms the trace genuinely flows
through the refactored executor and that the comparator is sensitive to sub-ULP-scale
change. The perturbation was applied by monkeypatch in a scratch script and never written
to the repository.

## 7. Proposed interface for B2

`KinematicProfile` already carries the fields B2 needs, currently inert:

| Field | B1 value | B2 use |
| --- | --- | --- |
| `context` | populated | conditioning key for the distribution sampler |
| `target_speed` | resolved scalar | drawn from a context-conditioned distribution |
| `speed_envelope_bl_s` | `None` | the envelope or distribution parameters for that context |
| `acceleration_limit` | `None` | bounded accel, replacing "accel is whatever damping yields" |
| `deceleration_limit` | `None` | separate decel behavior |
| `relaxation` / `relaxation_rate` | fixed per path | may itself become context-dependent or sampled |
| `turn_gain` | `1.0` | turn/saccade interaction scaling |
| `persistence_seconds` | `None` | history/persistence of a kinematic context |
| `spontaneous_clock_rate` | passed through | already context-dependent; keep |

Recommended B2 entry points, in order:

1. Give `KinematicResolver` a seeded RNG **with its own stream offset** (as
   `lifecycle.py` does with 18001), so new draws cannot perturb existing streams. This is
   the first change that will legitimately break bit-identity, and it should be isolated
   in its own step with an explicit before/after trace.
2. Introduce `room_kinematic_scale` as a single class-C config value applied at exactly
   one point inside the resolver, where BL/s becomes world units/s. Its value stays at
   the current effective mapping until deliberately changed.
3. Add the context-conditioned sampler behind `speed_envelope_bl_s`, leaving
   `acceleration_limit` inert for one further step.
4. Add `tools/kinematics_sanity.py` producing the distribution and bout metrics defined
   in plan section 10, before changing any value.

Constraints that carry forward: the executor must keep one exact code path per relaxation
law; no universal fly-speed constant may be created; simulation time, the 20 ms tick and
MaleCNS temporal dynamics stay unchanged; and hit rate and escape rate are reported but
never optimized against.

## 8. Known limitations of B1

1. The context label is not recorded. Making it visible in `ticks.jsonl` implies recorder
   schema 5 and was deliberately deferred so B1 could be accepted on exact identity.
2. Launch and stationary-contact velocities are still set directly in `World`; they are
   tagged `DIRECT` for context identity but not executed through the profile. Moving them
   would change M1.8-A code without behavioral benefit in B1.
3. The escape impulse remains in `World._move_fly` rather than the executor, because it is
   a neural action rather than an ecological kinematic request.
4. `speed_envelope_bl_s`, `acceleration_limit`, `deceleration_limit` and
   `persistence_seconds` are validated but unused. They are hooks, not behavior.
5. Bit-identity is demonstrated on this machine and toolchain (Windows, Python 3.11.16,
   `NUMBA_NUM_THREADS=4`). As with M1.7 replay, thread count still matters.

## 10. Status

B1 is accepted, committed and frozen as the structural baseline for M1.8-B2: the
resolver/profile/executor split, the one-exact-code-path-per-relaxation-law rule and the
inert B2 hook fields should not be reshaped without cause. B2 is not implemented and its
parameter values remain unchosen. No RL, reward function, personalized learning or
adaptive opponent policy exists anywhere in the codebase.
